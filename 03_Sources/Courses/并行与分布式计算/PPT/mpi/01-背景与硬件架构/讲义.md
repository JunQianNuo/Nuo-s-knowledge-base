# 第一讲：MPI 的硬件背景与 Git 协作入门

![现代计算集群中的机柜](../../../../../../04_Assets/Images/Courses/%E5%B9%B6%E8%A1%8C%E4%B8%8E%E5%88%86%E5%B8%83%E5%BC%8F%E8%AE%A1%E7%AE%97/PPT/mpi/01-%E8%83%8C%E6%99%AF%E4%B8%8E%E7%A1%AC%E4%BB%B6%E6%9E%B6%E6%9E%84/assets/nersc-racks-cc0.jpg)

**核心问题：**一个程序怎样从一台多核计算机扩展到多台计算机？扩展后，数据放在哪里，进程又怎样交换数据？如何用 Git 提交自己的练习改动并发起审查？

## 一、为什么还要学习 MPI？

OpenMP 让同一程序中的多个线程在共享内存环境下协作。线程可以访问共享变量，但需要处理数据竞争与同步。若问题所需内存或计算资源超出一台节点的能力，就需要把工作和数据分给多台节点。此时，一台节点上的普通内存地址不能被另一台节点上的程序直接当成本地地址使用；程序需要明确安排数据交换。

以二维网格为例：若有 $20\,000\times20\,000$ 个点，每个点的一个数按 8 字节计算，一份数组约需 $3.2$ GB；同时保存三份这样的数组约需 $9.6$ GB。算法设计不仅要数运算次数，还要问数据存在哪里，以及交换多少数据。

再看一幅超高分辨率图像。数字病理中的整张切片图像，解压后的数据可能达到数十 GB。假设一幅图像有 $100\,000\times100\,000$ 个像素，采用 RGB 三个颜色通道，每个通道占 1 字节，则一份像素数组需要 $30$ GB（以 $10^9$ 字节为 1 GB）。**这里算的是未压缩的像素数据**，尚未计入临时缓冲；JPEG、PNG 等压缩文件的大小还取决于图像内容和编码方式，不能直接当作内存需求。

一种组织办法是把图像沿两个方向各分成 10 份，得到 100 个 $10\,000\times10\,000$ 的图像块，每块的像素数据约为 $300$ MB。若 100 个 MPI 进程各负责一块，就可以分别读入自己的块，在各自的内存中完成逐像素亮度调整等处理，而不必让一个进程保存整幅图像。实际的分块尺寸和进程数可以不同；多个进程放在同一节点上时，仍需合计它们占用的节点内存。图像的存储块与进程的任务划分也不必一一对应。

处理后，各进程可以**并行输出自己的图像块**，并记录每块在整幅图中的位置，供后续程序按坐标读取或拼接。分块也可以由文件格式在内部组织，例如支持大文件的分块 BigTIFF，并不要求每块都成为一个独立文件；若多个进程要直接写入同一个文件，就需要约定数据布局，并使用支持协作写入的方式。这样的设计同时分担内存、计算和输出工作，但共享存储的带宽、块之间的数据交换和最终拼接仍可能成为瓶颈，100 个进程并不保证快 100 倍。

![高分辨率图像分块与并行输出示意图](../../../../../../04_Assets/Images/Courses/%E5%B9%B6%E8%A1%8C%E4%B8%8E%E5%88%86%E5%B8%83%E5%BC%8F%E8%AE%A1%E7%AE%97/PPT/mpi/01-%E8%83%8C%E6%99%AF%E4%B8%8E%E7%A1%AC%E4%BB%B6%E6%9E%B6%E6%9E%84/assets/image-tiles-parallel.svg)

图中只展示第 0、1、99 块的任务与输出，块的位置按行、列从 0 编号。每个进程处理自己的块，输出的位置记录让各块仍组成一幅完整图像。

MPI（Message Passing Interface）是消息传递程序的**接口标准**。它规定通信操作如何表达，不是一种处理器，也不是一台超级计算机。课程中的 Open MPI 是该标准的一种实现。MPI 程序可以在一台多核计算机上运行，也可以部署到多台通过网络连接的节点上。

## 二、一段简短的历史

![博物馆展出的 Cray-1](../../../../../../04_Assets/Images/Courses/%E5%B9%B6%E8%A1%8C%E4%B8%8E%E5%88%86%E5%B8%83%E5%BC%8F%E8%AE%A1%E7%AE%97/PPT/mpi/01-%E8%83%8C%E6%99%AF%E4%B8%8E%E7%A1%AC%E4%BB%B6%E6%9E%B6%E6%9E%84/assets/cray-1-museum-cc-by-sa.jpg)

1976 年推出的 Cray-1 是向量超级计算机的重要代表。它说明科学计算对高吞吐计算的需求由来已久，但**向量机并不等于 MPI 集群**。随后，多个处理器、多个计算节点协作解决同一问题日益常见，不同消息传递系统之间需要一个可移植的共同接口。MPI Forum 于 1990 年代初推动标准化，MPI 1.0 于 1994 年发布。

计算资源可以由**一台机器内部的多个核心**提供，也可以由**多台节点共同提供**。硬件组织方式改变后，程序组织数据和通信的方式也要随之改变。

## 三、从核心到集群：数据在哪里？

![计算资源层次示意图](../../../../../../04_Assets/Images/Courses/%E5%B9%B6%E8%A1%8C%E4%B8%8E%E5%88%86%E5%B8%83%E5%BC%8F%E8%AE%A1%E7%AE%97/PPT/mpi/01-%E8%83%8C%E6%99%AF%E4%B8%8E%E7%A1%AC%E4%BB%B6%E6%9E%B6%E6%9E%84/assets/hardware-hierarchy.svg)

- **核心（core）**执行指令；核心附近有寄存器和缓存。核心数表示可能并行执行的硬件资源之一，不等于 MPI rank 数。
- **CPU 插槽与 NUMA 域**组织多个核心和内存。某些多插槽机器仍给程序一个共享地址空间，但不同内存位置的访问代价可能不同。
- **计算节点（node）**是一台参与计算的计算机，通常有处理器、内存和操作系统。一个节点可以运行多个线程，也可以运行多个 MPI 进程。
- **集群与互联网络**把多台节点连接起来。节点之间交换数据需要通信机制，例如 MPI 的发送、接收与集合通信。

请沿着图回答：一个核心需要的数据可能来自哪里？若数据在另一台节点上，程序需要增加什么步骤？

### 硬件图提问的参考答案

核心使用的数据可能已在寄存器或缓存中，也可能需要从本节点主存取得。在 NUMA 系统中，访问不同位置的主存，代价可能不同。若所需数据位于另一台节点，程序应通过通信取得实际数据，将它放入接收进程可用的内存后再计算；普通本地指针不能直接访问另一台节点的内存。

## 四、线程、进程、rank 和节点不能混为一谈

| 名称 | 所属层次 | 含义 |
|---|---|---|
| 核心 | 硬件 | 执行指令的计算资源 |
| 线程 | 程序执行 | 同一进程内的一条执行路径；OpenMP 常用多个线程 |
| 进程 | 操作系统 | 运行中的程序实例；普通进程有自己的地址空间 |
| rank | MPI 通信 | 某个通信域中进程的编号，如 0、1、2、3 |
| 节点 | 计算机系统 | 一台参与计算的计算机，可承载多个进程 |

![同一节点可容纳多个 MPI rank](../../../../../../04_Assets/Images/Courses/%E5%B9%B6%E8%A1%8C%E4%B8%8E%E5%88%86%E5%B8%83%E5%BC%8F%E8%AE%A1%E7%AE%97/PPT/mpi/01-%E8%83%8C%E6%99%AF%E4%B8%8E%E7%A1%AC%E4%BB%B6%E6%9E%B6%E6%9E%84/assets/rank-placement.svg)

特别注意：`mpirun -np 4` 启动的是 **4 个进程**，并不自动意味着使用了 4 台节点。在本课程的单容器练习中，这些进程通常都位于同一计算环境。即使 MPI 实现在同节点进程之间使用共享内存传输数据，MPI 程序仍以**消息传递接口**表达通信；不要把底层传输方式与程序的通信模型混为一谈。

## 五、OpenMP 与 MPI：相同问题的两种组织方式

![共享内存与消息传递示意图](../../../../../../04_Assets/Images/Courses/%E5%B9%B6%E8%A1%8C%E4%B8%8E%E5%88%86%E5%B8%83%E5%BC%8F%E8%AE%A1%E7%AE%97/PPT/mpi/01-%E8%83%8C%E6%99%AF%E4%B8%8E%E7%A1%AC%E4%BB%B6%E6%9E%B6%E6%9E%84/assets/programming-models.svg)

假设要把一个长数组分成四段求局部和，再求总和：

- 用 **OpenMP**，四个线程可以访问同一进程中的数组；各算一段，最后通过规约汇总。程序要明确哪些数据共享、哪些数据私有。
- 用 **MPI**，四个进程各自处理一段数据；若某进程需要别的进程的结果，程序需通过 MPI 通信操作传递或汇总。数组如何分配到进程，是算法设计的一部分。

这不是“OpenMP 只能单机、MPI 只能跨机器”的绝对分界。现代多核节点上可以使用纯 MPI，也可以在节点间使用 MPI、节点内结合 OpenMP。

### 实例：ASPECT 如何并行模拟地幔？

**ASPECT** 是研究地幔对流等计算地球动力学问题的开源软件。官网给出一个尺度上的难题：地幔深度接近 $3\,000$ km，而值得追踪的局部地幔羽流直径可能只有几十 km。若整个模拟区域都采用能分辨最小结构的细网格，单元数量和计算、内存需求会迅速增长。ASPECT 因此采用自适应网格：在需要分辨局部变化的地方细化，其他地方保留较粗的网格；随着结构移动，网格也可能改变。

MPI 网格分区的价值是让多个进程分担网格、数据和计算，使更大的问题成为可能；自适应细化则把精度用在关键位置。通信、全局求解、输出和负载不均也会消耗时间，所以处理器数量翻倍不保证运行时间减半。后续课程中的热传导练习会复用“分区、计算、交换边界数据”的思想。

### 开源 MPI 实现：Open MPI 与 MPICH

MPI 标准规定通信接口的名称、参数和行为。要编译和运行 MPI 程序，还需要安装这个标准的具体实现。**Open MPI** 和 **MPICH** 都是开源的 MPI 实现，提供头文件、通信库，以及配套的编译和启动工具。

| 项目 | 简要介绍 | 本课程中的位置 |
|---|---|---|
| **Open MPI** | 由高校、科研机构和企业共同参与开发维护，面向高性能计算，支持多种系统与网络环境。 | 课程实验环境采用的 MPI 实现。 |
| **MPICH** | 强调高性能与可移植性，也是一些厂商 MPI 实现的基础。 | 了解另一种实现，认识 MPI 标准带来的源码可移植性。 |

写程序时，我们调用标准接口，例如 `MPI_Init`、`MPI_Send` 和 `MPI_Recv`；编译和运行时，使用所安装实现提供的工具。`mpicc` 是 C 编译器包装命令，负责补充 MPI 的头文件和库选项，再调用实际 C 编译器；`mpirun` 或 `mpiexec` 则组织启动 MPI 进程。这些命令与程序中调用的 MPI 函数处在不同环节。

只使用标准接口的源码，通常可以在支持这些接口的 Open MPI 或 MPICH 环境中重新编译运行。更换实现时，应使用对应的工具重新编译，并保持编译所链接的 MPI 库与启动环境一致。后面的练习通过 Makefile 统一调用编译和启动工具。

### 思考题

1. 四个 MPI rank 在同一台节点上运行，这还是 MPI 程序吗？为什么？
2. OpenMP 的四个线程可以访问一个共享数组。换成四个普通 MPI 进程后，rank 0 的普通指针能否直接作为 rank 1 的本地指针使用？
3. 看到四行乱序输出，能否只凭输出顺序判断四个执行者是否真的同时运行？
4. 参照 ASPECT 示意图，为什么分区边界可能需要通信？如果局部细化只发生在一个 rank 的区域，可能产生什么问题？
5. MPI 标准与 Open MPI、MPICH 是什么关系？`mpicc` 与程序中的 `MPI_Init` 分别负责什么？

### 思考题参考答案

1. **仍然是 MPI 程序。**判断依据是程序使用 MPI 接口组织进程协作，而不是进程是否跨节点。同节点通信可能采用共享内存传输，但程序仍通过 MPI 接口表达通信。
2. **不能直接使用。**四个普通进程各有自己的地址空间；传递一个指针数值，不会传递它指向的数据。即使两个进程中的地址数值相同，也不表示指向同一对象。通常应把实际数据传给另一个进程的接收缓冲区；专门建立共享内存是另一种需要明确安排的机制。
3. **不能断定。**操作系统调度、输出缓冲以及启动器汇集输出都会影响显示顺序。乱序输出不能证明同时执行，有序输出也不能证明顺序执行。输出编号可以帮助核对执行者，判断性能和并发还需要更多测量。
4. **边界计算可能依赖邻区的数据，因此需要通信。**若细化集中在一个 rank 的区域，其单元数、未知量数及计算和内存需求可能增加，造成负载不均；其他 rank 可能等待较慢者。可以考虑重新分区，但实际负载还取决于各单元的计算代价，不能只比较单元数量。
5. **MPI 是接口标准，Open MPI 与 MPICH 是具体实现。**`mpicc` 在编译阶段补充 MPI 头文件与库选项，再调用实际 C 编译器。`MPI_Init` 是每个进程在运行时调用的函数，用于初始化本进程的 MPI 环境；它不负责创建其他进程。启动多个进程通常由 `mpirun` 或 `mpiexec` 组织。

## 六、版本控制、Git 与课程仓库

### 从文件备份到分布式版本控制

版本控制记录文件随时间发生的变化，使我们能比较两个版本、找到一次修改的作者和原因，并在需要时恢复旧版本。手工复制 `final`、`final2` 文件也能留下一些版本，但很难可靠地管理多人修改。早期的 RCS 在本机保存历史；CVS、Subversion 等集中式系统把项目历史放在中央服务器；Git 属于分布式版本控制系统，**克隆仓库时也取得项目历史**，每个人可以先在本地提交，再与远端交换更新。

Git 诞生于 2005 年的 Linux 内核开发背景中。其设计重视速度、分支开发和分布式协作。Git 管理的对象是文件和提交历史；Gitee 是托管 Git 仓库并提供 Fork、Pull Request 等协作功能的平台。两者不能混为一谈。

### Git 如何保存一次修改？

![从工作区到 Pull Request 的 Git 协作流程](../../../../../../04_Assets/Images/Courses/%E5%B9%B6%E8%A1%8C%E4%B8%8E%E5%88%86%E5%B8%83%E5%BC%8F%E8%AE%A1%E7%AE%97/PPT/mpi/01-%E8%83%8C%E6%99%AF%E4%B8%8E%E7%A1%AC%E4%BB%B6%E6%9E%B6%E6%9E%84/assets/git-workflow.svg)

编辑器改动首先在**工作区**；`git add` 把选定的文件内容放进**暂存区**；`git commit` 将暂存的内容保存为**本地仓库中的一次提交**。提交包含项目状态的快照、作者、说明和与此前提交的关联。`git push` 把本地分支的提交送到远端仓库。**Pull Request（PR）**则是在 Gitee 网页上提出“请审查并考虑合并我的分支”的请求；推送成功不代表 PR 已创建，更不代表教师仓库已合并。

| 要解决的问题 | Git 操作 |
|---|---|
| 我改了哪些文件？ | `git status`、`git diff` |
| 哪些改动进入下一次提交？ | `git add`、`git diff --cached` |
| 怎样留下可追溯的版本？ | `git commit`、`git log --oneline` |
| 怎样让练习与主线分开？ | `git switch -c 分支名` |
| 怎样把本地提交传到自己的远端仓库？ | `git push` |

一次提交应围绕一个清楚的改动。本次练习只新增一个个人文档，查看差异后再提交；不要把无关的编译产物或其他练习改动一起加入暂存区。

记录当前环境可用的 CPU 逻辑处理单元数、OpenMP 最大线程数以及 MPI 自检中出现的 rank。**容器看到的资源不一定等于整台物理机器的完整拓扑**；这些输出只描述当前练习环境，不足以证明发生了跨节点网络通信。

#### 任务 A 参考答案：怎样解释输出？

- 脚本中的“CPU 核心数”由 `nproc` 给出，实际表示当前进程可用的处理单元数，通常对应逻辑 CPU，不能直接解释为物理核心数或节点数；具体数值应以自己的环境实测为准。
- `omp_get_max_threads()` 返回后续不显式指定线程数的并行域可使用的线程数上界。自检脚本没有创建 OpenMP 并行域，因此这个数不是已经实际运行的线程数。
- MPI 自检使用 `mpirun -np 4`。若成功启动四个进程，应看到 rank 集合 `{0, 1, 2, 3}`，各进程报告的进程总数均为 4；显示顺序可以变化。
- 这些结果不能证明使用了四台节点，也不能证明四个进程在硬件上同时执行。

### 任务 B：比较线程与进程

cd /workspace/examples/openmp/01_hello_world

cd /workspace/examples/mpi/01_hello_world

#### 任务 B 参考答案：编号与模型

| 命令 | 请求数 | 编号集合的参考答案 | 通信 / 内存模型 |
|---|---:|---|---|
| `OMP_NUM_THREADS=2 make run` | 2 | 实际线程数为 2 时：`{0, 1}` | 同一进程内的 OpenMP 线程，共享地址空间 |
| `OMP_NUM_THREADS=4 make run` | 4 | 实际线程数为 4 时：`{0, 1, 2, 3}` | 同一进程内的 OpenMP 线程，共享地址空间 |
| `make run NP=2` | 2 | 成功启动两个进程时：`{0, 1}` | MPI 进程，消息传递模型 |
| `make run NP=4` | 4 | 成功启动四个进程时：`{0, 1, 2, 3}` | MPI 进程，消息传递模型 |

OpenMP 实际线程数可能受动态调整、线程限制等影响，应以程序打印的 `Number of threads M` 为准，此时编号集合为 `{0, …, M−1}`。这个示例还会单独打印一行线程总数，因此不能把总输出行数直接当成线程数。MPI 示例中的 `size` 表示 `MPI_COMM_WORLD` 中的进程数。两种程序都应比较编号集合，不能只凭输出先后判断是否同时执行。

### 任务 C：画图并解释

画两台节点，每台画两个核心；在图上放置四个 MPI rank。然后回答：

1. 四个 rank 是否必须平均放在两台节点上？
2. 若 rank 0 要取得 rank 3 计算的数，按 MPI 的消息传递模型应发生什么？
3. 将四个 rank 都放到第一台节点时，答案的哪一部分会改变？哪一部分不会改变？

#### 任务 C 参考答案

1. **不必须平均放置。**“每台两个 rank”是一种可能的放置方式。进程位置由分配的资源、启动参数和映射规则决定，rank 编号本身不指定节点或核心。
2. **需要传递计算出的数值。**例如 rank 3 通过 `MPI_Send` 发送结果，rank 0 通过匹配的 `MPI_Recv` 接收；也可按算法选择适当的集合通信。传递 rank 3 的普通指针不能代替传递它指向的数据。
3. **改变的是进程位置和可能的底层传输路径；不变的是逻辑分工、rank 的含义与程序使用的 MPI 通信接口。**同节点通信可能采用共享内存传输，普通进程的地址空间仍不会因此自动合并。图中每台只有两个核心，若将四个 rank 都放在第一台，还需考虑启动器的可用槽位与是否允许超额运行；四个进程不保证四个同时执行。

### 观察结果的解释

- `-np 4` 表示四个 MPI 进程；rank 是进程在通信域中的编号，不是节点编号。
- 同节点 MPI 通信可能使用共享内存作为传输机制，跨节点通常依靠互联网络；程序调用 MPI 的方式可以保持一致。
- 线程与进程的输出都可能交错；输出顺序不能单独证明硬件上是否同时执行。
- 若未运行 `check_env.sh`，`/tmp/mpi_check` 可能不存在；先执行任务 A。

用编辑器打开复制出的 `git-practice/<自己的Gitee用户名>.md`，将模板中的提示改成自己的说明，至少解释：（1）rank 与节点的区别；（2）`commit`、`push`、PR 分别完成什么。文件名中的用户名应与上面的 `GITEE_USER` 一致。

```bash
git status
git diff
git add "git-practice/${GITEE_USER}.md"
git diff --cached --check

```

新文件尚未 `git add` 时，`git status` 会列出它，而普通 `git diff` 不显示这个未跟踪文件。`git diff --cached --check` 检查暂存内容中的空白错误；读 `git diff --cached`，确认暂存区只有自己的文档。`git log -1 --oneline` 中的短哈希标识这次提交；`git push` 将分支送到自己的 Fork。如果提示 `Permission denied (publickey)`，回到 SSH agent 检查，不要把私钥复制进容器。

#### Git 模板的参考答案

## 要点回顾

硬件上，计算资源从核心扩展到节点，再扩展到集群；软件上，OpenMP 通过线程共享内存协作，MPI 用进程和消息传递组织数据。**进程数不等于节点数**；rank 是进程在通信域中的编号，不是计算节点的编号。ASPECT 展示了网格分区与局部细化如何支撑大规模模拟，也说明通信和负载均衡必须纳入设计。Git 记录代码演变；个人分支上的提交先推送到自己的 Fork，再通过 Gitee Pull Request 提请课程仓库审查。
