# 标签数据库与检索补齐实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** 建立可维护的标准标签数据库，并让已有显式概念元数据进入 Obsidian 内置标签搜索。

**Architecture:** `总览/标签库/条目/` 中的 Markdown 记录是唯一词表数据源，原生 `总览/标签库.base` 提供数据库视图。Python 维护脚本按词表精确匹配现有元数据，局部补写 `tags`；默认只读，显式 `--apply` 才写入，并保存逐文件原始字节与哈希。

**Tech Stack:** Obsidian Bases、Markdown/YAML、Python 3 与现有 PyYAML、unittest。

**Spec:** `总览/审查报告/2026-10-26-标签检索审查与首批修复建议.md`；用户补充要求“统一标准名只要建立database就好了；其他的按你的方法解决”。

## Global Constraints

- 使用当前共享原子卡目录，不增加课程归属、迁移文件或重写正文。
- 保留 `topics`、自定义标签字段及全部无关元数据；实际搜索入口为 `tags`。
- 按官方标签字符规则校验；大小写不重复计数，斜杠仅表达层级。
- 不凭正文子串猜标签；DCT 的缩写映射限定在明确的控制收敛上下文。
- 数据库记录文件名使用“标签-”前缀，避免与现有知识卡同名而改变 Wiki-link 解析。
- 原生 Base 不会自动同步标签，维护脚本负责实际落盘；数据库本身不填 `tags`，避免混入学习资料搜索。
- 本轮在用户正在使用的知识库直接维护；不创建脱离活动 Obsidian 的工作树，不提交已有未提交改动。原始字节备份保存到库外独立目录。
- 用户已授权数据库和后续整理，本计划记录具体实现，连续执行，不重复索取执行方式或审批。

## Review Focus

- DCT 在非控制收敛语境不得自动改名。
- 同名知识卡与词表记录不能使原有短 Wiki-link 歧义增加。
- CRLF、BOM、正文、注释及无关元数据应原样保留。
- 活动 Obsidian 或其他任务修改过的文件，不得被过期扫描结果覆盖。
- 词表中的同义词只是映射配置，不能误称内置 `tag:` 搜索会自动识别旧名。
