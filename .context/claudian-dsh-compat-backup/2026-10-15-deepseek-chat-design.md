# Claudian DeepSeek 对话协议适配设计

## 目标与现状

目标是在当前机器的 Claudian 2.3.20 与 dsh 0.1.5-rc.1 之间恢复可验证的对话链路，而不再把“读取模型列表”当作“对话正常”。用户已同意继续完整修复并验证真实对话；本文是实施前的设计审阅稿，尚未修改运行中的插件。

已确认的事实：

- 当前插件保留前两次启动兼容补丁，SHA-256 为 `69d90e7f211385bd24879623bdc0e6676fad6333ae51c69cb922824c9d0c8422`。
- 实际 dsh 已复现 `job/list: no active Remote method exports this endpoint`，无需发送模型请求即可触发。
- 原生 `session/control` 的基线包括 `queues`、`jobs`、`projections`，并推送各自的更新。
- 现有 `DeepSeekSessionObserver` 仍订阅 `job/list`；现有 `DeepSeekRoster` 只识别 projection 更新，遇到 queue/jobs 更新也会失败。
- `DeepSeekJournal` 仍调用已移除的 `session/projections`；后台停止仍调用 `job/kill`。这些契约都必须核对，不能只删除当前报错。

## 路线选择

1. **推荐：迁移现有 DeepSeek provider 到已安装原生协议。** 保留 Host、Roster、Observer 的职责边界，在协议入口完成归一化。改动较集中，也能检验任务完成和取消的真实语义。
2. 在启动覆盖层模拟整套旧协议：表面改动小，但会出现两套状态和生命周期逻辑，不采用。
3. 回退 dsh：可能影响用户自己的原生客户端及存储兼容性，不作为本次默认方案。

## 设计

### 单一控制状态所有者

`DeepSeekRoster` 继续独占进程级控制订阅，维护同一代基线内的任务、队列和投影；其他组件读取派生状态，不另建一套同步标志。

- 基线必须整体安装后再发布 ready；重连先清空旧代，再安装新基线。
- 分别处理 queue、jobs、projection 帧，并验证实际原生字段。
- 缺失状态表示未知，不能当作空任务或空队列。
- 保留已有会话归属规则，不能因为扫描历史而激活冷子代理。

### 观察、消息与完成判断

`DeepSeekSessionObserver` 从 Roster 取得任务与队列，不再请求旧 `job/list`。`session/follow` 仍负责日志和 assistant stream；按请求身份关联用户提交与原生回合，保留去重、重连和追加式输出约束。

收到 turn/end 不等于全部工作结束：必须核对原生队列、子代理和后台任务，必要时由控制状态所有者重新建立基线，再发布空闲状态。测试覆盖不同流的乱序及合并推送。

### 历史与恢复

使用当前原生公开的只读会话信息及固定切点分页，替换 `session/projections` 的依赖。不能为了获得历史而 follow 或 resume 所有会话；不能删除 writer locks。首先用本次测试产生的会话验证重开与继续，不读取用户既有聊天正文作为测试材料。

### 取消与后台停止

保留“先撤回未领取 steer，再取消当前回合”的语义，严格限定为当前视图拥有的任务和子代理。

实施计划必须先完成当前安装包的停止契约核对和实机探测：核实 `session/cancel`、队列移除、子代理中断及后台任务停止各自可用的公开能力。不能假设 `job/kill` 仍存在，也不能把它的失败转换为停止成功。

若原生确无后台任务停止的 Remote 出口，应先给出基于公开 jobs 服务的最小、经过认证的调用桥接设计供审阅；不擅自增设宿主内部注入，不杀掉其他会话共享的 Host，不把此缺口藏在成功提示里。这个条件是发布门槛，不是允许跳过后台停止的降级方案。

### 保持不变的部分

- 不改密钥、模型默认值、MCP 配置、用户原生配置和已有会话文件。
- 不改其他 provider，不升级或降级原生 dsh，不重构聊天 UI。
- 保留前两次启动补丁，但重新验证其与本次变更的组合。
- 只使用当前原生 Web 安装进行本地资格验证；不宣称其他版本或 Desktop 已兼容。
- 如果涉及临时会话持久化契约变化，必须按 provider 指南验证 fork、子代理、长工具输出和图像/上传不落盘；未通过不能宣称临时会话隔离已合格。

## 验收

1. 测试先复现旧接口失败，再通过新协议测试；覆盖基线、更新、重连、流乱序、冷子代理以及取消。
2. 通过完整 execution session 路径进行少量、短内容的真实模型请求，不直接调用模型 API 绕过插件；不把 Vault 内容发作测试提示。
3. 一次普通文本问答返回非空响应，流输出结束且界面状态可回到空闲；紧接着第二条消息可以正常完成。
4. 在隔离临时目录验证一次受限工具调用，确认工具结果与结束状态一致，不写课程笔记。
5. 验证运行中取消、待处理消息撤回及后台任务停止，不误报成功、不重复回复、不影响无关会话。无法确认停止时明确报告失败。
6. 对测试会话验证分页与重开后继续；其他历史兼容性只能按实际验证范围报告。
7. 运行 typecheck、lint、完整测试、build 和最终产物性能检查。原版已存在失败必须按名称与基线比较并记录，不能声称全部测试通过。
8. 使用最终候选插件产物再次运行对话回归；只有通过后才备份并部署。记录源文件、补丁范围、哈希及配置未改动证据。
9. 不在当前会话中强制重载插件。部署后由用户重启 Obsidian，再在真实 UI 中确认；源码或测试脚本通过不能替代这一项。

## 实施顺序与审阅点

审阅本文后，先编写带文件清单、红绿测试和实机命令的实施计划，再按用户选择的执行方式实施。推荐本会话顺序实施，最后独立审查；无需为每个相邻组件分别派发实现代理。

发布报告分别列出已验证、未验证及不支持的行为。任何需要扩大桥接权限、改变原生配置、迁移存储或额外大规模模型消耗的方案，都另行说明，不包含在本设计的默认授权内。
