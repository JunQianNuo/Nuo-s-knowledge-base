# OpenMP同步结构的选择

> 一句话：先分清是要保护共享写入、让一项工作只做一次，还是等待一阶段完成，再选对应的 OpenMP 结构。

## 按需要选择

| 需要 | 结构 | 必须分清的边界 |
|---|---|---|
| 多个线程汇总部分和等 | `reduction` | 每线程先算私有副本，最后合并；适用于支持的归约运算 |
| 更新单个受支持的内存位置 | `atomic` | 只保护该原子操作，不能保护任意多语句不变量 |
| 多步共享状态更新 | `critical(name)` 或显式锁 | 同一锁域互斥；所有冲突访问必须遵守同一保护规则 |
| 任意一个线程做一次 | `single` | 执行者不固定；默认末尾有隐式屏障 |
| 由团队 0 号线程做 | `master` | 没有末尾隐式屏障；不等于其他线程随后立即可用结果 |
| 几段不同的独立任务 | `sections` | 每个 `section` 由某一线程执行一次；段数少则可能有线程空闲 |
| 所有线程完成本阶段再继续 | `barrier` | 团队所有线程须按一致顺序遇到该屏障 |
| 循环中的一个片段按迭代序提交 | `ordered` | 需配合循环的相应 `ordered` 子句，片段会串行化 |
| 省去允许省去的隐式屏障 | `nowait` | 不是同步操作；只有不存在未完成结果依赖时才能移除等待 |

`critical` 不是“整个团队只执行一次”：每个遇到它的线程都会执行，只是互斥。未命名临界区彼此互斥，同名临界区共用同一互斥域；不同名字不能保护同一共享变量上的冲突更新。

## 两个小例

局部计算已完成后，每线程合并一次：

```c
#pragma omp critical(sum_update)
{
    total += local_sum;
}
```

若循环本身就是求和，优先考虑 [[01_Knowledge/OpenMP循环分工与归约]] 的 `reduction(+:total)`。把每次迭代都放进临界区会把计算重新串行化。

任意一线程初始化、全体随后使用：

```c
#pragma omp parallel
{
    #pragma omp single
    {
        initialize_shared_data();
    } /* 默认屏障 */
    use_shared_data();
}
```

此处若换成 `single nowait`，其他线程可能先读到未初始化数据；换成 `master` 也需自行处理后续依赖。若只想按迭代序输出，可在带 `ordered` 子句的并行循环中把打印放进 `#pragma omp ordered`，不必把整个循环计算串行化。

## 显式锁的生命周期

```c
omp_lock_t lock;
omp_init_lock(&lock);
#pragma omp parallel
{
    omp_set_lock(&lock);
    update_shared_state();
    omp_unset_lock(&lock);
}
omp_destroy_lock(&lock);
```

使用前初始化；持锁代码的每条正常控制路径都要释放；所有使用结束后再销毁。多个锁的获取顺序不一致可能形成死锁。锁可灵活控制范围，但不应为简单归约引入额外复杂性。

## 选择前后的核查

列出共享位置和读写者：未同步的冲突访问至少一写时有数据竞争风险。`atomic` 能保护一次更新，却不能自动恢复 `a[i]` 依赖 `a[i-1]` 的顺序；此类问题须重设计算法或保留顺序，见 [[01_Knowledge/并行算法的数据依赖判定]]。工作共享循环、`single`、`sections` 通常有末尾隐式屏障，但 `master`、`critical` 没有团队屏障；并行域的末尾同步不能用 `nowait` 任意取消。通过不同线程数和重复运行核查结果与等待关系，再测量同步开销。
