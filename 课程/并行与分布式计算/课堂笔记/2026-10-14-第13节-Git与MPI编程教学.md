## 二、Git分支协作流程

不直接在主分支上修改，而是创建功能分支：

```bash
git checkout -b feature-name
```

修改后依次检查、暂存、提交：

```bash
git diff
git add path/to/file
git commit -m "describe the change"
```

第一次推送分支时建立上游关联：

```bash
git push --set-upstream origin feature-name
```

随后在代码托管平台发起Pull Request，将个人分支合并到目标仓库主分支。若存在冲突，必须先检查冲突文件、选择正确内容并重新提交，不能只为通过检查而机械删除冲突标记。

## 三、MPI程序的标准骨架

MPI程序通常按以下顺序组织：

```c
MPI_Init(&argc, &argv);

int rank, size;
MPI_Comm_rank(MPI_COMM_WORLD, &rank);
MPI_Comm_size(MPI_COMM_WORLD, &size);

/* local work and communication */

MPI_Finalize();
```

- `MPI_Init` 初始化MPI运行环境；
- `MPI_Comm_rank` 返回当前进程在通信域中的编号；
- `MPI_Comm_size` 返回通信域中的进程总数；
- `MPI_Finalize` 结束MPI环境。

`rank`与`size`通过地址传入，函数才能修改调用者的变量；漏写`&`会导致类型或运行错误。

## 四、通信域

通信域 `MPI_Comm` 同时规定参与通信的进程集合与消息匹配上下文。

- `MPI_COMM_WORLD` 包含本次MPI作业的全部进程；
- `MPI_COMM_SELF` 对每个进程而言只包含它自己，因此查询结果总是 `rank=0`、`size=1`；
- 将进程划分到不同通信域后，各组可以独立编号和通信，避免消息跨组误匹配。

rank始终是“相对于某个通信域”的编号，不是机器、CPU核心或进程的永久全局编号。

## 五、按rank分工与局部数据

可以通过条件判断给特定进程分配任务：

```c
if (rank == 0) {
    /* work for process 0 */
}
```

各MPI进程拥有独立地址空间。若所有进程都把局部变量 `value` 初始化为10，而rank 0把自己的值改为99，则只有rank 0看到99，其余进程仍为10。要让其他进程获得这个值，必须显式调用MPI通信函数；普通赋值不能跨进程传播。

终端输出顺序不固定，因为各进程独立调度。输出先后不能用来判断rank顺序或程序逻辑是否正确。

## 六、Makefile结构

课堂示例把编译器、运行器、进程数和目标文件写成变量，例如：

```makefile
CC ?= mpicc
NP ?= 4
TARGET := private_data
SRC := $(TARGET).c
```

`?=`表示只在变量尚未由命令行或环境指定时设置默认值，因此可在运行时覆盖进程数。

典型目标包括：

```makefile
all: $(TARGET)

$(TARGET): $(SRC)
	$(CC) $(CFLAGS) $< -o $@

run: $(TARGET)
	mpirun -n $(NP) ./$(TARGET)

clean:
	rm -f $(TARGET)
```

- 冒号左侧是目标，右侧是依赖；
- `$@`表示当前目标名，`$<`表示第一个依赖；
- `run`先确保程序已编译，再用指定进程数运行；
- `clean`删除生成物，便于重新构建。

## 八、易错点

1. 在主分支直接开发，导致提交难以审查和回退；
2. 忘记首次推送时建立远端上游分支；
3. 把rank当成CPU核心编号；
4. 忘记向 `MPI_Comm_rank` 和 `MPI_Comm_size` 传地址；
5. 以为同名局部变量会在进程间自动同步；
6. Makefile命令行未使用Tab缩进。
